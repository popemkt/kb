# Desktop editing and phone capture

Research record, 2026-11-18. Proposal for the owner, based on kb at `f3c078ff`.

## Decisions for the owner

| Decide | Recommended first release | What changes the choice |
| --- | --- | --- |
| Where does a store live? | Offer both a local desktop root with offline editing and a named remote kb over the tailnet. Choose one authority per store. | Editing the **same** store on two disconnected computers needs the separate [offline replication design](2026-10-31-offline-first.md). |
| What matters most on desktop? | Try Electron with the existing Bun release beside it. Favor reliable keyboard editing and a reproducible scene renderer over the smallest installer. Name the first desktop OS and oldest supported machine for the trial. | If installer size or memory dominates, qualify Electrobun with the system webview on that machine. |
| Which phone first? | Start on the owner's daily phone, with its native share receiver. Add the second platform against the same delivery tests. | A much larger mobile editing roadmap would justify sharing more UI code. |
| Where does one tap send an item? | Pin a named store and use its default capture target, or choose an explicit inbox node. Use the store's day at delivery for the default. | If a share made just before midnight must stay on that date, carry the capture date through the capture-target contract before shipping. |
| What should work away from the host? | Make the share durable on the phone immediately. Offer online graph search and local access to pending items. | A full offline phone search index would require a replica, conflict policy and storage budget. |
| Who can send? | Pair each phone from the chosen host, scope and revoke its credential there, and require the tailnet for remote access. Start with personal test builds. | Broader distribution needs a signing, update and support owner. |

## 1. Plugin design comes first

Install an application on a device and install a family into a store as two distinct operations. A local desktop window opens the page served by the packaged `kb ui`. A remote window opens the page served by that store's existing host. In either case the HTML, browser halves, action schemas and live socket come from the same build serving the store. The native shell owns windows, OS events and process lifetime. [Surfaces](../../DESIGN.md#surfaces) · [Extension families](../../DESIGN.md#extension-families)

| Existing owner | Local desktop | Remote desktop | Phone capture |
| --- | --- | --- | --- |
| Shared declaration and server entry | The Bun child opens the root using kb's runtime registry, store backend, actions, guards and seeds. | The remote process does this. | Invoke the registered actions at the selected host. |
| Optional `kb ui` host contributions | Starting the real CLI composes its agent adapters, secrets and routines services. OS credentials and optional executables belong to that host account. | The remote account supplies them. | Requires none on-device. Capture succeeds with agent and routines switched off. |
| Browser half | The React page resolves the enabled manifest rows. Bundled entries come from the build, repository page entries from the trusted closure named by its digest. | Same resolver inside the remote page. | The native receipt, compose and search screens consume action data. If opening the full page, load that host's ordinary page. |

Use the store's existing Settings for enable, install, update and trust. A required bundled family keeps its declared status. Switching an optional family off removes its contributions while retaining its data and install selection. Linked, installed and root-owned code follow host-side pin/closure and trust decisions. Changing the bytes requires trust for the new digest on the executing machine. A fresh local machine may need to obtain the pinned bytes and approve them before it can work offline. A remote client cannot confer that trust by installing its app. Desktop page plugins already run with page privileges. Keep the web contents sandboxed with no Node integration, shell execution, filesystem bridge or reusable phone credential. [CLI host composition](../../packages/app/cli/src/host-plugins.ts) · [Browser resolver](../../DESIGN-UI.md#extension-ui-halves) · [Electron security guidance](https://www.electronjs.org/docs/latest/tutorial/security)

**Capture placement already has an owner.** An ordinary `node.add` with omitted parent invokes `ui.capture-target`. On the registry, Days can plan today's missing ancestors in the same transaction. Core defaults to top level. An explicit inbox supplies its node ID as parent. Explicit null means top level. Native capture should honor this role even when another family wins it. Show the actual destination from committed graph data. A missing explicit inbox needs attention before delivery. Keep the queued item addressed to that inbox until the person retargets it. [Days and capture](../../DESIGN.md#days) · [Provider roles](../../DESIGN.md#provider-roles)

**Contract to prove.** Drive the same capture cases through desktop quick capture and both share receivers, inspect the resulting nodes through one-shot kb after closing the apps, and run the backend cases on JSONL and SQLite. Compare parent, field IDs, asset reference, receipt and refusal for an explicit inbox, store default, switched-off family and invalid destination. Share adapters translate OS inputs. Any new retry or mapping guarantee belongs in the action contract used by every caller. There is no reason to add a fourth family half or maintain a mobile list of enabled plugins. [One contract, every implementation](../../AGENTS.md#one-contract-every-implementation)

## 2. Desktop host choice

All four can display React. Only a local Bun process supplies kb's filesystem, SQLite, extension loader and host services when disconnected. The current release contains split CLI chunks and the matching UI, and looks up Bun via `KB_BUN` or PATH. Ship an architecture-matched runtime and preserve that layout and its launch flags. Windows packaging needs its own launch proof because today's entry script is POSIX shell. [Release builder](../../bin/release-bundle)

| Candidate | Runtime, size and scenes | Desktop integration and updates |
| --- | --- | --- |
| **Electron + Bun child** | Largest expected baseline. Ships Chromium and Node in addition to kb and Bun. A pinned Chromium makes keyboard, scene and fallback regressions reproducible. Driver availability still matters. | BrowserWindow for main and capture windows, menu, tray, globalShortcut and registered protocol. Wayland shortcuts depend on the desktop portal. Built-in updates on macOS/Windows, package/distribution strategy on Linux. [Shortcuts](https://www.electronjs.org/docs/latest/api/global-shortcut/) · [Deep links](https://www.electronjs.org/docs/latest/tutorial/launch-app-from-url-in-another-app) · [Updater](https://www.electronjs.org/docs/latest/api/auto-updater) |
| **Tauri v2 + Bun sidecar** | Rust shell uses WKWebView, WebView2 or WebKitGTK. Saves a bundled browser, still pays for Bun and kb. Test actual WebGPU and WebGL fallback on the oldest supported OS. Build and locate the sidecar per target. | Native menus, tray, multiple webview windows, deep-link and global-shortcut plugins, signed updater artifacts. Good small-shell candidate if system engines pass. [Webviews](https://v2.tauri.app/reference/webview-versions/) · [Sidecars](https://v2.tauri.app/develop/sidecar/) · [Shortcuts](https://v2.tauri.app/plugin/global-shortcut/) · [Updates](https://v2.tauri.app/plugin/updater/) |
| **Electrobun** | Bun main process is the closest runtime fit. Try using its packaged Bun for the existing child, including worker and dynamic extension loading. System webview saves bytes. Optional bundled CEF trades some of that advantage for a pinned engine. | Windows, menus, tray, URL-open and global shortcut hooks plus patch updates. Menu/tray behavior varies by platform. Verify signed replacement, rollback and Bun version compatibility before committing. [Runtime and engines](https://docs.electrobun.dev/electrobun/guides/compatability/) · [Main process API](https://docs.electrobun.dev/electrobun/apis/main/) · [Update architecture](https://docs.electrobun.dev/electrobun/guides/architecture/overview/) |
| **Installed web app** | Smallest incremental install. Browser supplies the engine and the host supplies Bun. Installing the page alone does not deliver a local store or start its process. A separately running local kb would still work offline. | Standalone windows and kb's panes, deploy updates with the served page. OS-wide hotkey, tray, native menus and reliable custom-scheme handling would need another component. Good baseline for remote use. [Installed web apps](https://developer.chrome.com/docs/capabilities/pwa-install) |

Start with **Electron** because the main workload is editing the existing full page, including scenes, on every supported desktop. Bundling Bun costs space but keeps the running kb identical to the CLI release. Electrobun is the comparison worth building first alongside it. Measure the two complete applications before setting an installer budget. Tauri adds Rust and a Bun sidecar while retaining the system-webview qualification cost. An installed page is already close to the remote experience and misses the global capture gesture.

**Window behavior.** Open one workspace window per chosen store, with ordinary keyboard navigation, selection, undo, palette, existing split panes and focused-pane route. New Window gets its own tab session. Native menu commands dispatch the same page commands with the focused pane's context. A configurable system hotkey raises one small capture window over the current app, showing the pinned store, destination and focused text field. Enter submits, Escape dismisses, and focus returns to the previous app. Keep input on failure. The tray offers the same command if a shortcut is taken. A proposed `kb://open/<store-key>/<node-id>` resolves a known store and opens its node in the focused pane. Treat the link as navigation only. [Panes and layouts](../../DESIGN-UI.md#panes-and-layouts)

**Store lifecycle.** Keep the display name separate from a stable registration key, as in bb's named-store selector. Resolve each key to a local root or a configured HTTPS origin. For a local root, validate live kb presence, reuse a compatible host or start an owned loopback child on an available port. Two windows on one root share that host. Quit stops only owned children, after pending writes settle. Persist window layout per store/window and test port changes across restarts because page storage is origin-scoped. Remote loss shows the page's connection state. A local root remains editable without Internet, subject to the network needs of individual adapters. Never silently redirect a disconnected remote window into a local copy.

## 3. Phone host choice

| Option | What happens when the user chooses kb in another app |
| --- | --- |
| **Native Swift/Kotlin receiver and thin containing app** | iOS Share Extension reads supported attachments from extension items, copies them into an App Group container and completes the request. Android registers a receiving activity for ACTION_SEND and, for multiple files, ACTION_SEND_MULTIPLE. Copy content URI bytes while the temporary grant is valid. Smallest path from share sheet to durable handoff. [Apple share extension](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/Share.html) · [Shared containers](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/ExtensionScenarios.html) · [Android receiving](https://developer.android.com/training/sharing/receive) |
| **Tauri v2 mobile** | Reuse web code for compose/search. Still integrate the iOS extension target and Android intent entry, with Swift/Kotlin plugins where the webview cannot run. Attractive if the phone grows a substantial web UI. [Mobile plugins](https://v2.tauri.app/develop/plugins/develop-mobile/) |
| **Expo / React Native** | Share TypeScript screens. Expo documents experimental incoming-share support. Prove receipt and persistence with the containing app cold or terminated, including on iOS, before relying on a JS callback. Custom native targets/modules and local builds remain possible. [Expo Sharing](https://docs.expo.dev/versions/latest/sdk/sharing/) · [App extensions](https://docs.expo.dev/build-reference/app-extensions/) |
| **PWA Web Share Target** | An installed supporting Android browser can pass text, URLs and files to the manifest's share_target. Useful Android prototype. iOS needs a native target for inbound system sharing. Outbound navigator.share solves a different gesture. [Chrome receiving shared data](https://developer.chrome.com/docs/capabilities/web-apis/web-share-target) |

Choose the native receivers. Both speak the same small capture contract. The containing app needs a store picker, text compose field, pending deliveries and online `graph.search` results that open the selected node. Starting React or connecting the VPN must never be a prerequisite to dismissing a successful share.

**Pairing and reachability.** Use an existing Tailscale connection on the phone to reach the chosen host's HTTPS public origin. The documented Linux deployment proxies to a private Unix socket, with the optional trusted login header supplied by Serve. Store selection binds a device registration to one store authority. Pin that binding in every queued item so renaming a store works and deleting/reusing its display name cannot redirect old captures. Refuse an endpoint whose pairing identity changed. [Tailnet serving and caller identity](../../DESIGN.md#action-registry)

A native POST has no browser Origin. Today's guard assigns it the program wire, even when an identity provider returns a name. Page actor and approval are **declared, not proven** (gap `01M413SP3QSSQJMKKDK3W3J6G8`). Tailnet membership or a proxy login alone cannot establish which installed device made a capture. Propose a short-lived, single-use pairing challenge approved on the host, exchanging it over TLS for a revocable device credential in iOS Keychain or Android Keystore-backed storage. Bind the server-side grant to store, device and allowed operations. Require it at the phone ingress, derive actor on the server and forbid approval, trust and install there. Scope the capture operation to its destination and grant search separately since search reveals graph text. The phone must lack an alternate route to the unrestricted page/program API under that grant. Test this at deployment ingress as well as in the action guard. Extend the existing identity provider and wire admission together. Merely recognizing the credential in a provider does not change the no-Origin branch. This would close the device-specific case of W3J6G8 only. [Request guard](../../packages/app/server/src/guard.ts) · [Identity providers](../../packages/app/server/src/auth.ts)

**Queue and confirmation.** Persist a capture UUID, paired store key, destination choice, capture timestamp, text/URL and owned attachment files before acknowledging the share. Stage files first, then atomically publish the queue entry. Clean abandoned staging files. This device-local spool holds pending delivery, with the repo's off-graph reason recorded where it is implemented. Drain immediately when reachable, retry on foreground/reconnect, and schedule best-effort background transfer (iOS shared-container background URLSession, Android WorkManager). OS scheduling and VPN availability put no bound on delivery time. On loss of credentials pause for re-pairing. On a permanent refusal keep the item for correction or explicit discard. [Apple background transfer](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/ExtensionScenarios.html) · [Android persistent work](https://developer.android.com/develop/background-work/background-tasks/persistent)

Choosing kb in the OS share sheet is the submit gesture after initial setup. Return to the source app showing “Queued on this phone · Personal” after durable local acceptance or “Saved to Personal” after a host receipt. The containing app shows queued items, failures with a reason, and an Open node action for a delivered item. If storage is full or a payload is unsupported, show the error in the receiver before dismissing. Searching offline shows pending captures and explains that graph search needs the host.

## 4. What a share writes

| Shared payload | Proposed graph result |
| --- | --- |
| URL and optional title | Create one node using the supplied title or URL as its text. Put the full URL in the store's configured URL-typed field by ID. Configure/seed that field once during setup. Preserve any separate selected text as a child. No metadata fetch on the share-sheet path. |
| Plain text | Create one node preserving Unicode and line breaks. Treat a sole valid HTTP(S) URL as a link. Keep prose containing a link intact. |
| Image | Copy bytes before completing the OS request. Apply the existing asset acceptance rules, invoke `asset.upload` (`asset_upload` on MCP), then use the returned relative path in the node's Markdown image reference. For a group, keep one parent with ordered attachment children. Check size before base64 expansion and explain any refused format. [Asset implementation and 25 MiB limit](../../packages/application/operations/src/assets.ts) |

Both apps should submit the same normalized payload. Put mapping and replay semantics at the action owner. The existing upload generates a fresh asset ID on every call. A timeout after upload, or after node commit but before receipt, makes a blind retry unsafe. Spike a store-scoped idempotency key bound to the payload and device, deterministic or recoverable staged asset ownership, and a durable receipt linked atomically to node creation. A retry must recover the same node and attachment and a reused key with different content must fail. Exercise concurrent deliveries and crash recovery before promising exactly one visible result. Retain queued bytes until the host acknowledges the committed node.

## 5. Evidence and delivery order

**Packaging probe actually run.** On Linux x64 in the Nix shell, built `sh bin/release-bundle` with Bun 1.4.2. The compressed kb tarball occupied 6.8 MiB on disk. The separate installed Bun executable occupied 76 MiB **uncompressed**. These numbers use different encodings and cannot be added to estimate a download. Started the release launcher with `ui --no-open --port 0` for two fresh roots concurrently, one initialized with `--store sqlite --bare`, one with JSONL. Both served HTTP 200 at their respective loopback roots. Posted a different `node.add` to each, stopped both servers, then searched with the packaged one-shot CLI. Each returned just its own item. An initial run reported an unwritable shared UI build cache. The repeated two-store run used temporary KB_HOME, KB_DATA and XDG_CACHE_HOME. Include writable per-user cache paths in the launcher test. This tested Bun packaging and store isolation. GUI startup, WebGPU, OS share sheets, background delivery and installers still need device measurements.

| Phase | Experiment or increment | Evidence required to proceed |
| --- | --- | --- |
| 0 · Desktop comparison | Frame the release page in Electron and Electrobun on the owner's primary OS. Add one global hotkey, two root windows and a remote window. Repeat on each proposed supported OS before claiming support. | Record compressed installer, installed bytes, idle RSS, cold time to editable row and warm hotkey-to-focus p95 on named hardware. Compare typing, IME, selection, clipboard, WebGPU scene and forced WebGL fallback with the same page in its usual browser. Reject any shell that loses edits, leaks native privileges or cannot restore focus reliably. |
| 0 · Phone lifecycle | Use a local simulator/emulator and the owner's available device. Share URL, multiline text, image and oversize image from real source apps. Exercise lock screen, cold start, extension termination, airplane mode and later reconnect. | Time share-to-dismiss, kill between file copy and queue commit, and repeat across midnight. Each acknowledged item must survive restart in the intended store. Record which background retries actually run. Use personal local builds where signing permits. |
| 1 · Contracts | Prove paired-device admission and recoverable capture over both store adapters. Use existing node/asset actions for their semantics. Extract common ownership first where a new guarantee spans calls. | Shared contract suite covers lost acknowledgements, concurrent retries, revoked/wrong-store credentials, changed family settings and unavailable inbox. One receipt and one referenced copy of each attachment after recovery. |
| 2 · Desktop pilot | Ship the winning shell for one OS with main and capture windows, named roots/origins and navigation-only deep links. | Offline local reopen, second CLI writer, remote disconnect, second window close and owned-child crash all preserve the store. Test update and rollback with local artifacts. An app update must preserve data and follow kb's existing migration approvals. |
| 3 · Phone pilot | Ship the first native receiver and minimal app to the owner for local trial. Add the second OS once it passes the same cases. | Revoke one device while another keeps working. Queue into A, switch to B, reconnect and verify A alone received the item. Reconcile phone state with a one-shot read. |

**Gap accounting.** Candidate gaps for implementation are durable capture replay including assets, paired and restricted native admission, stable named-store binding across reconnects, and per-window state across changing loopback origins. Record a graph gap at the implementation site if any guarantee is deferred. Device admission narrows W3J6G8. Full offline multi-writer replication, marketplace changes and distribution to app stores are separate decisions. The proposed pilots use local builds and an existing tailnet.
