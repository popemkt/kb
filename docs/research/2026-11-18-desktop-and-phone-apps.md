# Desktop editing and phone capture

Research record, 2026-11-18. Proposal for the owner, based on kb at `f3c078ff`.

## Decisions for the owner

| Decision | Recommendation |
| --- | --- |
| Which desktops must the first release support? | Name the oldest supported OS/device and set a download or idle-memory budget before the trial. Start with Electron for its pinned Chromium. Choose Tauri if its system webviews pass the same WebGPU scene, WebGL fallback, editing and shortcut tests, its Rust shell can ship and update the Bun sidecar reliably, and the complete app meets a footprint budget Electron misses. |
| Where will the pilot store live? | Choose either a local desktop root for offline editing or a remote HTTPS URL. The desktop loads its UI from whichever host serves that store. A phone needs a reachable URL for delivery, including when the desktop hosts the store. |
| Which phone gets the first receiver? | Start with the owner's daily phone. Both receivers keep the original share and show pending and sent items. Pair one revocable device credential per store. Check the host's capture-contract version at pairing and before sending. A mismatch leaves shares queued with an explanation. |
| How should the host file delayed captures? | Use the store's configured capture target or an explicit inbox configured on the host. With Days selected, use the store's day at delivery unless the owner prefers the original capture date. The raw payload retains its timestamp either way. |
| Is a link preview worth fetching? | Display a supplied title if available. Start without a fetch. If previews prove useful, enrich the saved node asynchronously on the host. |

## 1. Plugin design comes first

Install an application on a device and install a family into a store as two distinct operations. A local desktop window opens the page served by the packaged `kb ui`. A remote window opens the page served by that store's existing host. In either case the HTML, browser halves, action schemas and live socket come from the same build serving the store. The native shell owns windows, OS events and process lifetime. [Surfaces](../../DESIGN.md#surfaces) · [Extension families](../../DESIGN.md#extension-families)

| Existing owner | Local desktop | Remote desktop | Phone capture |
| --- | --- | --- | --- |
| Shared declaration and server entry | The Bun child opens the root using kb's runtime registry, store backend, actions, guards and seeds. | The remote process does this. | Deliver the original share to one versioned capture action at the selected host. |
| Optional `kb ui` host contributions | Starting the real CLI composes its agent adapters, secrets and routines services. OS credentials and optional executables belong to that host account. | The remote account supplies them. | Requires none on-device. Capture succeeds with agent and routines switched off. |
| Browser half | The React page resolves the enabled manifest rows. Bundled entries come from the build, repository page entries from the trusted closure named by its digest. | Same resolver inside the remote page. | The pending/sent list reads local delivery state and host receipts. It needs no family UI. |

Use the store's existing Settings for enable, install, update and trust. A required bundled family keeps its declared status. Switching an optional family off removes its contributions while retaining its data and install selection. Linked, installed and root-owned code follow host-side pin/closure and trust decisions. Changing the bytes requires trust for the new digest on the executing machine. A fresh local machine may need to obtain the pinned bytes and approve them before it can work offline. A remote client cannot confer that trust by installing its app. Desktop page plugins already run with page privileges. Keep the web contents sandboxed with no Node integration, shell execution, filesystem bridge or reusable phone credential. [CLI host composition](../../packages/app/cli/src/host-plugins.ts) · [Browser resolver](../../DESIGN-UI.md#extension-ui-halves) · [Electron security guidance](https://www.electronjs.org/docs/latest/tutorial/security)

**Capture placement already has an owner.** An ordinary `node.add` with omitted parent invokes `ui.capture-target`. On the registry, Days can plan today's missing ancestors in the same transaction. Core defaults to top level. An explicit inbox supplies its node ID as parent. Explicit null means top level. The proposed host capture action supplies the configured inbox ID or leaves the parent to the role, including when another family wins it. A missing configured inbox produces a refusal. After the owner repairs the setting, retry the original queued share. [Days and capture](../../DESIGN.md#days) · [Provider roles](../../DESIGN.md#provider-roles)

**Contract to prove.** Drive the same capture cases through desktop quick capture and both share receivers, inspect the resulting nodes through one-shot kb after closing the apps, and run the backend cases on JSONL and SQLite. Compare parent, field IDs, asset reference, receipt and refusal for an explicit inbox, store default, switched-off family and invalid destination. Run the same mixed text, URL and two-file fixture through each adapter and verify the host receives the original values, file order and bytes. Any new retry or mapping guarantee belongs in the action contract used by every caller. There is no reason to add a fourth family half or maintain a mobile list of enabled plugins. [One contract, every implementation](../../AGENTS.md#one-contract-every-implementation)

## 2. Desktop host choice

All four can display React. Only a local Bun process supplies kb's filesystem, SQLite, extension loader and host services when disconnected. The current release contains split CLI chunks and the matching UI, and looks up Bun via `KB_BUN` or PATH. Ship an architecture-matched runtime and preserve that layout and its launch flags. Windows packaging needs its own launch proof because today's entry script is POSIX shell. [Release builder](../../bin/release-bundle)

| Candidate | Runtime, size and scenes | Desktop integration and updates |
| --- | --- | --- |
| **Electron + Bun child** | Largest expected baseline. Ships Chromium and Node in addition to kb and Bun. A pinned Chromium makes keyboard, scene and fallback regressions reproducible. Driver availability still matters. | BrowserWindow for main and capture windows, menu, tray, globalShortcut and registered protocol. Wayland shortcuts depend on the desktop portal. Built-in updates on macOS/Windows, package/distribution strategy on Linux. [Shortcuts](https://www.electronjs.org/docs/latest/api/global-shortcut/) · [Deep links](https://www.electronjs.org/docs/latest/tutorial/launch-app-from-url-in-another-app) · [Updater](https://www.electronjs.org/docs/latest/api/auto-updater) |
| **Tauri v2 + Bun sidecar** | Rust shell uses WKWebView, WebView2 or WebKitGTK. Saves a bundled browser, still pays for Bun and kb. Test actual WebGPU and WebGL fallback on the oldest supported OS. Build and locate the sidecar per target. | Native menus, tray, multiple webview windows, deep-link and global-shortcut plugins, signed updater artifacts. Good small-shell candidate if system engines pass. [Webviews](https://v2.tauri.app/reference/webview-versions/) · [Sidecars](https://v2.tauri.app/develop/sidecar/) · [Shortcuts](https://v2.tauri.app/plugin/global-shortcut/) · [Updates](https://v2.tauri.app/plugin/updater/) |
| **Electrobun** | Bun main process is the closest runtime fit. Try using its packaged Bun for the existing child, including worker and dynamic extension loading. System webview saves bytes. Optional bundled CEF trades some of that advantage for a pinned engine. | Windows, menus, tray, URL-open and global shortcut hooks plus patch updates. Menu/tray behavior varies by platform. Verify signed replacement, rollback and Bun version compatibility before committing. [Runtime and engines](https://docs.electrobun.dev/electrobun/guides/compatability/) · [Main process API](https://docs.electrobun.dev/electrobun/apis/main/) · [Update architecture](https://docs.electrobun.dev/electrobun/guides/architecture/overview/) |
| **Installed web app** | Smallest incremental install. Browser supplies the engine and the host supplies Bun. Installing the page alone does not deliver a local store or start its process. A separately running local kb would still work offline. | Standalone windows and kb's panes, deploy updates with the served page. OS-wide hotkey, tray, native menus and reliable custom-scheme handling would need another component. Good baseline for remote use. [Installed web apps](https://developer.chrome.com/docs/capabilities/pwa-install) |

Use **Electron as the reference build**. Its pinned Chromium reduces the number of browser engines to qualify for the keyboard-first outliner and GPU scenes. Tauri buys a smaller shell by using the OS webview. WebGPU availability and scene behavior can then change across OS versions, and the local store still needs a Bun sidecar packaged and updated alongside Rust. Give Tauri the same full-page trial on the oldest supported machines. If it matches Electron on editing, scene rendering and fallback, focus and hotkey behavior, survives a sidecar upgrade, and meets an agreed download or memory limit Electron exceeds, **choose Tauri**. Include Electrobun to measure how much the Bun-native shell saves with the same kb payload.

**Window behavior.** Open one workspace window per chosen store, with ordinary keyboard navigation, selection, undo, palette, existing split panes and focused-pane route. New Window gets its own tab session. Native menu commands dispatch the same page commands with the focused pane's context. A configurable system hotkey raises one small capture window over the current app, showing the pinned store, destination and focused text field. Enter submits, Escape dismisses, and focus returns to the previous app. Keep input on failure. The tray offers the same command if a shortcut is taken. A proposed `kb://open/<store-key>/<node-id>` resolves a known store and opens its node in the focused pane. Treat the link as navigation only. [Panes and layouts](../../DESIGN-UI.md#panes-and-layouts)

**Store lifecycle.** Keep the display name separate from a stable registration key, as in bb's named-store selector. Each key resolves to either a local desktop root or a remote HTTPS URL. For either target the serving host supplies its own UI, browser halves and registry. Desktop shell and host can update independently without introducing a separately versioned copy of the kb page. For a local root, validate live kb presence, reuse a compatible host or start an owned loopback child on an available port. Two windows on one root share that host. Quit stops only owned children, after pending writes settle. Persist window layout per store/window and test port changes across restarts because page storage is origin-scoped. Remote loss shows the page's connection state. A local root remains editable without Internet, subject to the network needs of individual adapters. Never silently redirect a disconnected remote window into a local copy.

## 3. Phone host choice

| Option | What happens when the user chooses kb in another app |
| --- | --- |
| **Native Swift/Kotlin receiver and thin containing app** | iOS Share Extension reads supported attachments from extension items, copies them into an App Group container and completes the request. Android registers a receiving activity for ACTION_SEND and, for multiple files, ACTION_SEND_MULTIPLE. Copy content URI bytes while the temporary grant is valid. Smallest path from share sheet to durable handoff. [Apple share extension](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/Share.html) · [Shared containers](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/ExtensionScenarios.html) · [Android receiving](https://developer.android.com/training/sharing/receive) |
| **Tauri v2 mobile** | Reuse web code for the delivery list. Still integrate the iOS extension target and Android intent entry, with Swift/Kotlin plugins where the webview cannot run. Attractive if the phone grows a substantial web UI. [Mobile plugins](https://v2.tauri.app/develop/plugins/develop-mobile/) |
| **Expo / React Native** | Share TypeScript screens. Expo documents experimental incoming-share support. Prove receipt and persistence with the containing app cold or terminated, including on iOS, before relying on a JS callback. Custom native targets/modules and local builds remain possible. [Expo Sharing](https://docs.expo.dev/versions/latest/sdk/sharing/) · [App extensions](https://docs.expo.dev/build-reference/app-extensions/) |
| **PWA Web Share Target** | An installed supporting Android browser can pass text, URLs and files to the manifest's share_target. Useful Android prototype. iOS needs a native target for inbound system sharing. Outbound navigator.share solves a different gesture. [Chrome receiving shared data](https://developer.chrome.com/docs/capabilities/web-apis/web-share-target) |

Choose native receivers. Selecting kb in the share sheet enqueues the item and returns the person to the source app. After pairing, the containing app needs just a pending/sent list with the store name, delivery state and any failure reason. A pending row can be retried or discarded. A sent row carries the host receipt.

**Keep the original share.** Preserve the text and URL as supplied, including when both are present, any supplied title, and the ordered files with their original bytes, filenames and declared types where available. Record the source app when the OS supplies it and the capture timestamp with its UTC offset. Leave unavailable source metadata absent. Copy files while the extension or intent still has permission to read them. A delivery envelope adds the paired store key, capture UUID and contract version. Parent, field and asset IDs are the host's responsibility.

Stage the files, then atomically publish the queue entry before showing “Queued on this phone · Personal.” If the phone runs out of space, show the failure while the receiver is open. Clean up uncommitted staging files. Keep queued payloads through restarts and failed sends. After the host returns the committed receipt, mark the item sent and release the copied bytes. Record the queue's device-local purpose at its implementation site. Attempt delivery when reachable, retry on foreground or reconnect, and use best-effort background transfer. A sleeping desktop or disconnected tailnet can delay delivery until the next app launch. [Apple background transfer](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/ExtensionScenarios.html) · [Android persistent work](https://developer.android.com/develop/background-work/background-tasks/persistent)

**Pair once per store.** The owner approves a one-use code on the host. Exchange it over tailnet HTTPS for one revocable, store-bound device credential in Keychain or Android Keystore-backed storage. The credential permits capture and discovery of its contract version. Pin the pairing to the store in each queue entry so changing the default store cannot redirect pending shares. A revoked credential pauses delivery for re-pairing. On the host, verify the credential and derive the device identity at admission. Today's no-Origin request uses the program wire, and caller-declared actor/approval (gap `01M413SP3QSSQJMKKDK3W3J6G8`) cannot prove a person's approval. A capture credential conveys no such approval. [Tailnet serving](../../DESIGN.md#action-registry) · [Request guard](../../packages/app/server/src/guard.ts)

**Check compatibility twice.** Propose that the capture action advertise the wire versions it accepts in `kb.manifest`. At pairing, show whether this phone and host share a version. Before each delivery, check that the host still accepts the queued envelope's version, then include that version in the call for the host to validate. This covers a host update between discovery and submission. If the action is missing or the version is incompatible, keep accepting shares locally and retain the original bytes. A pending row can say “Queued · Personal accepts v2. This capture uses v1.” Resume when the host accepts that version or a phone update can losslessly encode the original share for a supported version. A failed request for the manifest while offline simply leaves delivery pending.

## 4. One host action maps the share

Desktop quick capture and both native receivers call the same proposed registry action. Its input is the original share and delivery envelope. Its successful receipt identifies the committed node and store. The host validates the version, checks for an earlier receipt, applies the store's mapping and resolves the parent through its capture target or configured inbox. Clients do no graph writes of their own for a capture.

| Host receives | Host writes |
| --- | --- |
| URL, optional title and selected text | Use the supplied title or URL for node text. Put the original URL in the configured URL-typed field by ID and preserve separate selected text as a child. |
| Plain text | Preserve Unicode and line breaks. The host can recognize a sole HTTP(S) URL and apply the store's link mapping. |
| One or more files | Apply the existing `asset.upload` validation and storage mechanism (`asset_upload` on MCP). Reference each returned relative path from the capture node or ordered attachment children. A host refusal identifies the offending file and leaves the share pending. [Asset implementation and 25 MiB limit](../../packages/application/operations/src/assets.ts) |

**Link previews.** The share receiver can display a supplied title immediately. Keep networking off the share-sheet path. If the owner enables enrichment, a host job can fetch missing metadata after commit. A slow site, a preview error or a user edit to the title must leave the original share and its successful receipt intact.

**Replay.** Today's asset upload allocates a fresh ID per call. A lost acknowledgement between upload and node creation can otherwise duplicate files on retry. Inside the single capture action, bind the UUID to store, device and payload content, stage assets recoverably, and commit the receipt with the node. A concurrent or repeated submission returns the original receipt, including after a host restart. Reject reuse of the UUID with different content. Prove crash recovery on both store backends.

## 5. Evidence and delivery order

**Packaging probe actually run.** On Linux x64 in the Nix shell, built `sh bin/release-bundle` with Bun 1.4.2. The compressed kb tarball occupied 6.8 MiB on disk. The separate installed Bun executable occupied 76 MiB **uncompressed**. These numbers use different encodings and cannot be added to estimate a download. Started the release launcher with `ui --no-open --port 0` for two fresh roots concurrently, one initialized with `--store sqlite --bare`, one with JSONL. Both served HTTP 200 at their respective loopback roots. Posted a different `node.add` to each, stopped both servers, then searched with the packaged one-shot CLI. Each returned just its own item. An initial run reported an unwritable shared UI build cache. The repeated two-store run used temporary KB_HOME, KB_DATA and XDG_CACHE_HOME. Include writable per-user cache paths in the launcher test. This tested Bun packaging and store isolation. GUI startup, WebGPU, OS share sheets, background delivery and installers still need device measurements.

**Gap accounting.** Candidate gaps for implementation are a versioned raw capture action with durable replay including assets, paired and restricted native admission, stable named-store binding across reconnects, and per-window state across changing loopback origins. Record a graph gap at the implementation site if any guarantee is deferred. Device admission narrows W3J6G8. Full offline multi-writer replication, marketplace changes and distribution to app stores are separate decisions. The proposed pilots use local builds and an existing tailnet.
